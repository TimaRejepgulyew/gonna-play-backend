# gonna-play-backend

Бэкенд приложения для поиска футбольных матчей: Fastify + Prisma (PostgreSQL) + Redis.

## Тесты

Раннер — [Vitest](https://vitest.dev) 3.2.7. Набор разделён на два проекта, и разница между ними определяет, что нужно поднимать перед прогоном.

**`unit`** гоняет сервисный слой и утилиты с подменёнными репозиториями и in-memory заглушкой Redis. Ни сети, ни базы данных: клиенты инфраструктуры берутся ленивыми геттерами (`getPrisma()`, `getRedis()`), а заглушка занимает слот Redis через `setRedis()` до того, как до него доберётся реальное создание клиента. Файлы идут параллельно.

**`integration`** поднимает приложение через `buildApp()` и бьёт по нему `app.inject()` с настоящими PostgreSQL и Redis. Данные чистятся перед каждым тестом (`TRUNCATE ... RESTART IDENTITY CASCADE` плюс `FLUSHDB`), поэтому файлы гоняются строго последовательно в одном форке.

### Поднять инфраструктуру

```bash
docker compose -f docker-compose.test.yml up -d db redis
DATABASE_URL=postgresql://postgres:postgres@localhost:5434/gonna_play_db_test npm run test:setup
```

`test:setup` — это `prisma migrate deploy` и только он. Сид не запускается намеренно: очистка перед каждым тестом снесла бы сид-пользователей до первого же ассерта, поэтому предусловием они быть не могут.

Тестовый стек живёт в собственном compose-проекте `gp-test` и на собственных портах — **PostgreSQL на 5434, Redis на 6381**. Разведение по портам здесь не косметика:

- 5432 занят dev-базой (`docker-compose.dev.yml`), 5433 — прод-стеком, 6380 — dev-Redis;
- очистка между тестами выполняет `TRUNCATE` по таблицам и `FLUSHDB` по всей логической базе Redis. `FLUSHDB` **игнорирует `keyPrefix`** и сносит ключи с любыми префиксами.

Отсюда правило: если `DATABASE_URL` или `REDIS_URL` укажут на dev- или прод-инстанс, прогон уничтожит их данные. Единственная реальная изоляция — раздельные инстансы, а не префикс ключей. Хелпер очистки дополнительно бросает при `NODE_ENV !== "test"`, но на этот гард полагаться как на единственную защиту не стоит.

### Команды

| Команда | Что делает | Требует инфраструктуры |
| --- | --- | --- |
| `npm run test:unit` | Только юнит-проект: сервисы и утилиты | Нет |
| `npm run test:integration` | Только интеграционный проект: HTTP через `app.inject()` | PostgreSQL + Redis |
| `npm test` | Оба проекта, **без подсчёта покрытия** | PostgreSQL + Redis |
| `npm run test:watch` | Тот же набор в watch-режиме | По проекту |
| `npm run test:coverage` | Оба проекта плюс отчёт покрытия и проверка порога | PostgreSQL + Redis |
| `npm run test:setup` | `prisma migrate deploy` на тестовую базу | PostgreSQL |

Полный прогон в контейнерах, без локально поднятой инфраструктуры:

```bash
docker compose -f docker-compose.test.yml up --abort-on-container-exit
```

Контейнер `backend` сам применяет миграции и запускает `npm run test:coverage`.

### Покрытие живёт в `test:coverage`, не в `npm test`

`npm test` прогоняет тесты и ничего не измеряет — это осознанное решение, а не пробел. Порог покрытия проверяет только `npm run test:coverage`, и именно эта команда стоит в `command` контейнера `backend`: CI в репозитории нет, и контейнерный прогон — единственное место, где порог срабатывает автоматически.

Текущий порог (`vitest.config.ts`): statements 47, branches 81, functions 41, lines 47. **Это не цель по качеству.** Числа сняты с прогона обоих проектов, в котором матчевых тестов нет вовсе: матчевый домен переписывается параллельно и вынесен в отложенную фазу, а `src/match/match.service.ts` — самый крупный файл домена. Порог показывает лишь «не стало хуже» и подлежит пересмотру вверх сразу после появления матчевых тестов.

### Переменные окружения

Значения тестового прогона выставляет `tests/setup/env.ts` — он грузится первым в `setupFiles` обоих проектов, до первого импорта чего-либо из `src/`. Отдельный `.env.test` для прогона **не обязателен**: без него набор работает на значениях из `env.ts`.

Существенно там следующее. `RATE_LIMIT_ENABLED` присваивается жёстко в `"false"`, а не через `??=`: логин ограничен 10 запросами за 900 секунд отдельно по IP и по email, а набор логинится многократно и упёрся бы в 429. `REDIS_KEY_PREFIX` уводится в `gptest:` — это удобство при отладке ключей, изоляцией оно не является (см. `FLUSHDB` выше). `DATABASE_URL` и `REDIS_URL` указывают на 5434 и 6381 соответственно.
