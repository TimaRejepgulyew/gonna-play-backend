# gonna-play-backend

Бэкенд приложения для поиска футбольных матчей: Fastify + Prisma (PostgreSQL) + Redis.

## Тесты

Раннер — [Vitest](https://vitest.dev) 4.1.10. Набор разделён на два проекта, и разница между ними определяет, что нужно поднимать перед прогоном.

**`unit`** гоняет сервисный слой и утилиты с подменёнными репозиториями и in-memory заглушкой Redis. Ни сети, ни базы данных: клиенты инфраструктуры берутся ленивыми геттерами (`getPrisma()`, `getRedis()`), а заглушка занимает слот Redis через `setRedis()` до того, как до него доберётся реальное создание клиента. Файлы идут параллельно.

**`integration`** поднимает приложение через `buildApp()` и бьёт по нему `app.inject()` с настоящими PostgreSQL и Redis. Данные чистятся перед каждым тестом (`TRUNCATE ... RESTART IDENTITY CASCADE` плюс `FLUSHDB`), поэтому файлы гоняются строго последовательно в одном форке.

### Поднять инфраструктуру

```bash
docker compose -f docker-compose.test.yml up -d db redis
DATABASE_URL=postgresql://postgres:postgres@localhost:5434/gonna_play_db_test npm run test:setup
```

`test:setup` — это `prisma migrate deploy` и только он. Сид не запускается намеренно: очистка перед каждым тестом снесла бы сид-пользователей до первого же ассерта, поэтому предусловием они быть не могут.

Тестовый стек живёт в собственном compose-проекте `gp-test` и на собственных портах — **PostgreSQL на 5434, Redis на 6381**. Разведение по портам здесь не косметика:

- 5432 занят dev-базой (`docker-compose.dev.yml`), 5433 — прод-стеком, 6380 — dev-Redis;
- очистка между тестами выполняет `TRUNCATE` по таблицам и `FLUSHDB` по всей логической базе Redis. `FLUSHDB` **игнорирует `keyPrefix`** и сносит ключи с любыми префиксами.

Отсюда правило: если `DATABASE_URL` или `REDIS_URL` укажут на dev- или прод-инстанс, прогон уничтожит их данные. Единственная реальная изоляция — раздельные инстансы, а не префикс ключей. Хелпер очистки дополнительно бросает при `NODE_ENV !== "test"`, но на этот гард полагаться как на единственную защиту не стоит.

### Команды

| Команда | Что делает | Требует инфраструктуры |
| --- | --- | --- |
| `npm run test:unit` | Только юнит-проект: сервисы и утилиты | Нет |
| `npm run test:integration` | Только интеграционный проект: HTTP через `app.inject()` | PostgreSQL + Redis |
| `npm test` | Оба проекта, **без подсчёта покрытия** | PostgreSQL + Redis |
| `npm run test:watch` | Тот же набор в watch-режиме | По проекту |
| `npm run test:coverage` | Оба проекта плюс отчёт покрытия и проверка порога | PostgreSQL + Redis |
| `npm run test:setup` | `prisma migrate deploy` на тестовую базу | PostgreSQL |

Полный прогон в контейнерах, без локально поднятой инфраструктуры:

```bash
docker compose -f docker-compose.test.yml up --abort-on-container-exit
```

Контейнер `backend` сам применяет миграции и запускает `npm run test:coverage`.

### Покрытие живёт в `test:coverage`, не в `npm test`

`npm test` прогоняет тесты и ничего не измеряет — это осознанное решение, а не пробел. Порог покрытия проверяет только `npm run test:coverage`, и именно эта команда стоит в `command` контейнера `backend`. Workflow `.github/workflows/quality.yml` покрытие не считает — он гоняет только линт (см. «Линт-гейт»), поэтому контейнерный прогон остаётся единственным местом, где порог покрытия срабатывает автоматически.

Текущий порог (`vitest.config.ts`): statements 47, branches 81, functions 41, lines 47. **Это не цель по качеству.** Числа сняты с прогона обоих проектов, в котором матчевых тестов нет вовсе: матчевый домен переписывается параллельно и вынесен в отложенную фазу, а `src/match/match.service.ts` — самый крупный файл домена. Порог показывает лишь «не стало хуже» и подлежит пересмотру вверх сразу после появления матчевых тестов.

### Переменные окружения

Значения тестового прогона выставляет `tests/setup/env.ts` — он грузится первым в `setupFiles` обоих проектов, до первого импорта чего-либо из `src/`. Отдельный `.env.test` для прогона **не обязателен**: без него набор работает на значениях из `env.ts`.

Существенно там следующее. `RATE_LIMIT_ENABLED` присваивается жёстко в `"false"`, а не через `??=`: логин ограничен 10 запросами за 900 секунд отдельно по IP и по email, а набор логинится многократно и упёрся бы в 429. `REDIS_KEY_PREFIX` уводится в `gptest:` — это удобство при отладке ключей, изоляцией оно не является (см. `FLUSHDB` выше). `DATABASE_URL` и `REDIS_URL` указывают на 5434 и 6381 соответственно.

## Линт-гейт

Соглашения о коде проверяются автоматически. Проверок две, и они всегда идут парой: `biome ci .` (форматирование, порядок импортов, размер файла, иерархия импортов, вложенные циклы через GritQL-плагин `biome/plugins/no-nested-loops.grit`) и `node scripts/check-comments.mjs` — отдельный процесс Node, считающий бюджет комментариев в `src/**/*.ts`. Вторая проверка живёт вне Biome, потому что метрика построчная и своего правила под неё в Biome нет; отсюда и своя область, зеркалящая `files.includes` из `biome.json`, — исключения Biome на отдельный процесс не действуют.

### Команды

| Команда | Что делает | Код выхода |
| --- | --- | --- |
| `npm run lint` | Обе проверки по всему дереву: `biome ci .`, затем бюджет комментариев | 0 чисто, ненулевой при нарушениях |
| `npm run lint:comments` | Только бюджет комментариев по `src/**/*.ts` | 0 чисто, 1 нарушения, 2 скрипт сломался сам |
| `npm run lint:report` | Печатает таблицу метрик по каждому файлу: непустые строки, комментарии, доля, длина серии | Всегда 0 — это отчёт, а не гейт |
| `npm run lint:fix` | `biome check --write .` — чинит то, что Biome умеет чинить сам | — |

`lint:report` отделён от `lint:comments` намеренно: он ничего не запрещает и нужен, когда порог предстоит пересмотреть — числа для решения берутся из его вывода, а не из головы. Код 2 у `lint:comments` тоже разведён с кодом 1 сознательно: собственная поломка скрипта не должна выглядеть как «нарушений не найдено».

### Четыре точки принуждения

Одна и та же пара проверок стоит в четырёх местах. Они различаются областью и тем, что происходит при срабатывании.

| Точка | Что запускает | Область | Последствие |
| --- | --- | --- | --- |
| Хук `PostToolUse` (`.claude/settings.json`) | `scripts/check-comments.mjs --hook-stdin` | Один файл, только что записанный агентом | Диагностика возвращается агенту сразу (`exit 2`); коммит и прогон не затрагиваются |
| `.githooks/pre-commit` | `biome check` и `check-comments.mjs` по staged-файлам | Только staged-файлы | Коммит отклоняется |
| `docker-compose.test.yml` | `npm run lint` первым шагом `command` | Всё дерево | Контейнерный прогон падает до миграций и до тестов |
| `.github/workflows/quality.yml` | `yarn lint` на Node 24 | Всё дерево | Push и pull request помечаются красным |

Порядок здесь — от узкого и быстрого к широкому и медленному. Хук `PostToolUse` смотрит ровно один файл и молчит, если путь пустой, не разобрался или лежит вне области, — иначе агент получал бы ложную диагностику на каждой записи файла вне `src/`. Pre-commit берёт только staged-файлы, чтобы не платить за весь репозиторий на каждом коммите. Линт в контейнере стоит **первым**, до `prisma migrate deploy`: он не требует базы, поэтому нарушение всплывает раньше самого долгого этапа. Workflow — последняя сетка, ловящая то, что обошли локально.

Содержимое `.githooks/` исполняется у каждого, кто поставил зависимости, а блок `hooks` в `.claude/settings.json` — у каждого, кто открыл репозиторий в Claude Code. Изменения в этих двух местах требуют на ревью такого же внимания, как изменения в CI.

### Установка хуков

Отдельного шага не нужно: lifecycle-скрипт `prepare` в `package.json` выполняет `git config core.hooksPath .githooks` при установке зависимостей. Проверено на yarn 1.22.22; скрипт идемпотентен и не падает там, где `.git` нет (например, при установке зависимостей внутри образа).

Если хуки всё же не встали — проверить настройку и поставить её вручную:

```bash
git config --get core.hooksPath   # ожидается .githooks
git config core.hooksPath .githooks
```

### Обход pre-commit

`git commit --no-verify` пропускает pre-commit целиком. Это осознанно оставленный аварийный выход, а не дефект: локальный хук не должен запирать работу, когда коммит нужен срочно. Он ничего не прощает — то же нарушение поймает контейнерный прогон и workflow, а с точки зрения гарантий гейта единственное, что защищено от локального обхода, это две удалённые точки.

## Обновление платформы: PostgreSQL 18 и Redis 8

Compose-файлы работают на образах `postgres:18` и `redis:8-alpine`. Для эфемерных dev- и test-томов достаточно пересоздать их (`docker compose ... down -v && up -d`).

Существующие prod-тома от PostgreSQL 13 **напрямую несовместимы** с PostgreSQL 18: формат данных мажорной версии не читается новым сервером, а том смонтирован по новому пути. В compose точка монтирования сменилась с `/var/lib/postgresql/data` на `/var/lib/postgresql` — PostgreSQL 18 хранит данные в подкаталоге, привязанном к версии, внутри этого каталога. Обновить прод с данными можно двумя путями: логическим — `pg_dump` на PG13 и `pg_restore`/`psql` в свежий PG18-том; или на месте — через `pg_upgrade` между бинарями обеих версий. Просто подменить тег образа на существующем томе нельзя — сервер не поднимется.

Локально рекомендуется (но не обязательно) синхронизировать версии brew-пакетов `postgresql` и `redis` с образами, чтобы CLI-утилиты (`pg_dump`, `psql`, `redis-cli`) совпадали с сервером по мажору.
