# Срез: venues-media

Площадки с фотографиями и локацией, объектное хранилище и аватары.

## Границы

Площадки (`Venue`), их фотографии (`VenuePhoto`), модуль `storage` для загрузки файлов и аватары пользователей. Матчи только ссылаются на площадку — сам срез матчей отдельно ([matches](matches.md)).

## Владеет таблицами

- `Venue` (name, city?, address?, latitude?, longitude?, capacity?)
- `VenuePhoto` (venueId, key, sortOrder)
- Модуль `storage` (обёртка над объектным хранилищем; своих таблиц нет).

## Касается

- `User.avatar` — ключ аватара в хранилище (запись).
- `Match.venueId` — только как ссылка со стороны матчей.

## Эндпоинты (под префиксом `/v1`)

- `POST/GET/PATCH/DELETE /v1/venues` — CRUD площадок.
- `POST /v1/venues/:id/photos/presign` — получить presigned URL для загрузки фото; после загрузки `POST /v1/venues/:id/photos` подтверждает и сохраняет `key`.
- `DELETE /v1/venues/:id/photos/:photoId` — удалить фото (и объект в хранилище).
- `POST /v1/users/me/avatar/presign` — presigned URL для аватара; подтверждение сохраняет `key` в `User.avatar`.

## Зависит от

`auth` (кто загружает и чьи это площадки/аватары).

## Что сделать

1. Схема `Venue`, `VenuePhoto` (+ поле `address`); миграция.
2. Модуль `storage` на S3-совместимом API (AWS SDK): `presignPut(key)`, `delete(key)`, построение CDN-URL для чтения. Работает с AWS S3 и MinIO — провайдер из конфигурации.
3. Эндпоинты presign и подтверждения; в БД сохраняются только ключи объектов, файл клиент льёт напрямую в хранилище.
4. Переменные окружения: бакет, endpoint, учётные данные, базовый URL CDN.

## Готово когда

Можно создать площадку с фотографиями через presigned-загрузку и загрузить аватар; чтение идёт по CDN-URL; в БД лежат только ключи, файлы через бэкенд не проходят.

## Открытый вопрос

Модель площадки — одиночный `Venue` против `Location + Field` (О1 в [../decisions.md](../decisions.md)). Пока проектируем на `Venue`. Если понадобится несколько полей на одной площадке — вернуться и разбить; это затронет `Match.venueId`.
