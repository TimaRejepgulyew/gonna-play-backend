# Срез: venues-media

Площадки (`Location` + `Field`) и — отдельной, ещё не начатой частью — медиа: объектное хранилище, фотографии и аватары.

## Границы

Площадки моделируются парой `Location` (комплекс) + `Field` (поле внутри комплекса) — CRUD обоих. Медиа-часть (модуль `storage`, фотографии, аватары) в код ещё не заведена. Матчи только ссылаются на поле — сам срез матчей отдельно ([matches](matches.md)).

## Владеет таблицами

- `Location` (name, city, address?, country?, latitude?, longitude?, surfaceType?, capacity?, openingHours?) — есть в схеме.
- `Field` (locationId, name, format, surface?, width?, length?, isIndoor) — есть в схеме.
- Медиа (`storage`, фотографии) — ещё не заведены.

## Касается

- `User.avatar` — сейчас просто строка; в перспективе ключ объекта в хранилище.
- `Match.fieldId` — ссылка со стороны матчей на конкретное поле.

## Эндпоинты

Площадки — реализованы, под префиксами `api/location` и `api/field` (перенос под `/v1` — за срезом [versioning](versioning.md)):

- `POST/GET/PATCH/DELETE /api/location` и `/api/field` — CRUD. `POST` закрыт `authorize("admin")`.

Медиа — ещё не реализованы (целевые):

- presigned-загрузка фотографий поля/комплекса и подтверждение с сохранением ключа;
- `POST /v1/users/me/avatar/presign` — presigned URL для аватара, подтверждение сохраняет ключ в `User.avatar`.

## Зависит от

`auth` (кто загружает и чьи это площадки/аватары).

## Что сделать

Площадки (`Location` + `Field`) с CRUD уже есть. Остаётся медиа и несколько уточнений:

1. Модуль `storage` на S3-совместимом API (AWS SDK): `presignPut(key)`, `delete(key)`, построение CDN-URL для чтения. Работает с AWS S3 и MinIO — провайдер из конфигурации.
2. Эндпоинты presign и подтверждения; в БД сохраняются только ключи объектов, файл клиент льёт напрямую в хранилище.
3. Переменные окружения: бакет, endpoint, учётные данные, базовый URL CDN.
4. Фотографии `Location` и `Field`: хранения и загрузки изображений площадок и полей нет вовсе. Нужна таблица под ключи фотографий (для поля и/или комплекса) и presigned-загрузка. Клиент из-за этого снял картинку поля в карточке списка и блок изображения на детали матча.
5. `POST /v1/users/me/avatar`: загрузки аватара нет — `User.avatar` остаётся просто строкой, записать в неё ключ нечем. В интерфейсе клиента загрузки не было, фиксируется как известный пробел.
6. Атрибуты площадки и поля (произвольные метки вида «трибуны», «освещение», «душ»): в схеме их нет ни у `Location`, ни у `Field`. Клиент удалил блок чипов на детали матча — класть их некуда.
7. Заведение площадки обычным пользователем: `POST /api/field/` и `POST /api/location/` закрыты `authorize("admin")` (`src/field/field.routes.ts:39`, `src/location/location.routes.ts:39`), при том что `POST /api/match/` требует существующий `fieldId`. Организатор матча не может создать площадку под свой матч — нужна либо роль `organizer` в проверке, либо отдельный маршрут заявки.
8. `GET /api/field/list` не отдаёт вложенную `location`: список идёт через `findMany` без `include` (`src/field/field.repository.ts:39-42`), тогда как `getField` её подмешивает (`:58`). Подтверждено живым запросом. Из-за расхождения пикер площадок в форме создания матча не может показать город и адрес одним запросом и вынужден либо склеивать с `GET /api/location/list` по `locationId`, либо показывать одно название.

## Готово когда

Площадки: CRUD `Location` и `Field` работает (сделано). Медиа: можно загрузить фотографии и аватар через presigned-загрузку, чтение идёт по CDN-URL, в БД лежат только ключи (**остаётся**).
