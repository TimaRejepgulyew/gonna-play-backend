# Срез: feature-flags

Примитивная система feature flags в БД для постепенной выкатки возможностей.

## Границы

Хранение флагов, вычисление на запрос с кешем, админ-управление и таргетинг по проценту и по версии приложения. Разбор самой версии приложения — срез [versioning](versioning.md).

## Владеет таблицами

- `FeatureFlag` (key unique, description?, enabled, rolloutPercent, platform?, minAppVersion?). Связей с доменом нет.

## Касается

- Читает платформу и версию приложения из запроса (их кладёт плагин версионирования).

## Эндпоинты (под префиксом `/v1`)

- `GET /v1/admin/feature-flags`, `POST /v1/admin/feature-flags`, `PATCH /v1/admin/feature-flags/:key` — управление (роль admin).
- Клиенту флаги отдаются вычисленными для вызывающего — через декоратор `request.featureFlags` и/или `GET /v1/feature-flags`.

## Зависит от

`versioning` (платформа и версия для таргетинга), `auth` (роль admin для управления).

## Что сделать

1. Схема `FeatureFlag`; миграция.
2. Плагин Fastify: вычисляет флаги на каждый запрос — `enabled`, затем `rolloutPercent` (детерминированный хеш по `userId`), затем ограничения `platform` и `minAppVersion`. Кеш значений в памяти с TTL, инвалидация при изменении флага.
3. Админ-CRUD под ролью admin.
4. Таргетинг берёт `request.platform` и `request.appVersion` из плагина версионирования.

## Готово когда

Флаг можно включить и выключить; процентная раскатка детерминирована для пользователя; таргетинг по платформе и версии работает; админ управляет флагами через API.
