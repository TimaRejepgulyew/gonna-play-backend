# Журнал решений

Каждая запись — принятое проектное решение с контекстом и статусом. Это то, что нельзя вывести из кода; при расхождении с базовым справочником скила приоритет здесь.

## Принятые

**Р1. Рейтинг — самооценка.** Игрок сам указывает уровень (`PLAYER_LEVEL`: junior…legend). Нет Elo, нет оценок после матча, нет сущности `PlayerRating` и таблицы истории. Разбивка команд опирается на уровень (вес junior=1…legend=4) и позицию. Выбор пользователя, перекрывает базовую доменку скила. Решение подтверждено 2026-07-23 и остаётся в силе.

> Отклонение в коде (на 2026-07-23): в схеме и в `src/rating/*` есть незапланированный модуль оценок после матча — таблица `player_ratings` и эндпоинты `POST/GET/DELETE /api/rating`. Это прямо противоречит Р1 и помечено к удалению из кода, а не к переносу в модель. См. запись в [PROGRESS.md](PROGRESS.md).

**Р2. Вход и провайдеры.** Email с паролем и вход через Telegram — сейчас; Apple — позже. Пересмотрено 2026-07-23 под фактическую реализацию: внешние провайдеры пока хранятся колонками на `User` (`telegramId`, `telegramUsername`, `isTelegramVerified`), отдельной таблицы `AuthIdentity` нет. Её заводим, когда появится второй внешний провайдер (Apple) и колонок станет мало; до тех пор это задел на будущее, а не текущая модель. Токены: короткий access-JWT плюс ротируемый refresh с детекцией повторного использования; состояние refresh-токенов лежит в **Redis** (`src/auth/refreshStore.ts`), а не в таблице `RefreshToken` — таблицы нет.

**Р3. Оплата.** У матча есть цена как число (`price?`), реальных платежей нет; `paymentStatus` у участника ведётся вручную. Задел под будущую сущность `Payment` и провайдера.

**Р4. Feature flags — примитивный сервис в БД.** Таблица `FeatureFlag(key, enabled, rolloutPercent, platform?, minAppVersion?)` плюс плагин Fastify (вычисляет флаги на запрос с кешем) и админ-эндпоинты. Готовый опен-сорс (Unleash / GrowthBook) отклонён ради простоты инфраструктуры.

**Р5. Версионирование по User-Agent.** Версия API — в URL как префикс `/v1`. Версия и платформа приложения приходят в заголовке `User-Agent` (например `GonnaPlay/2.3.0 (ios)`), их разбирает плагин: используется для мягкого требования обновиться (минимальная поддерживаемая версия) и для таргетинга флагов.

**Р6. Postman из OpenAPI.** Коллекция Postman не ведётся руками, а генерируется из спецификации OpenAPI, которую отдаёт `@fastify/swagger`, чтобы не расходиться с кодом.

**Р7. Медиа и хранилище.** Фото площадок (`VenuePhoto`) и аватары (`User.avatar`) хранятся в объектном хранилище, в БД — только ключи. Код на S3-совместимом API (AWS SDK), работает с AWS S3 и с self-hosted MinIO; провайдер выбирается на деплое. Загрузка — presigned URL (клиент льёт файл прямо в хранилище), чтение — через CDN. Локация площадки = широта/долгота + адрес.

**Р8. Фоновые задачи — node-cron.** На старте внутренний планировщик (напоминания, закрытие записи, лист ожидания, отметка не пришедших). Путь роста при нескольких копиях сервиса — очередь на Redis (BullMQ), потому что `node-cron` сработает в каждой копии.

**Р9. Площадка — `Location + Field`.** Пересмотрено 2026-07-23 под фактическую реализацию (изначально 2026-07-12 планировался одиночный `Venue`). Площадка моделируется парой: `Location` — комплекс (название, город, адрес, координаты, покрытие по умолчанию, вместимость, часы работы), `Field` — конкретное поле внутри комплекса (формат, покрытие, размеры, крытое или открытое). Матч ссылается на `Field` через `Match.fieldId`. Это совпадает с базовым справочником скила (там тоже `Location + Field`), так что расхождение по площадке снято. Медиа (`VenuePhoto` и хранилище) в коде пока нет — это незапущенный TODO среза `venues-media`.

## Расхождения с базовым справочником скила

Скиловый `.claude/skills/backend-design/references/domain-model.md`:

1. **Рейтинг** — там `PlayerRating` (оценки после матча). Здесь — самооценка (Р1). **Governs: эта вика.** При этом код по ошибке реализовал вариант скила (`player_ratings`), это отклонение к удалению — см. Р1.
2. **Площадка** — там `Location + Field`, и с 2026-07-23 вика тоже на `Location + Field` (Р9). Расхождение снято, отдельного governs не требуется.

Правило: при конфликте побеждает вики. Агенты скила, читающие `domain-model.md`, должны свериться с этим файлом.
